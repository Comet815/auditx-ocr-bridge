## F1 行号回映：公式成立的前提没被校验过（高嫌疑，先裁决这个）

**机制**：块文件 = 前导区 `pre_end` 行 + 1 个空行 + body。模型看到的是这个**完整文件**。
而 `remap_lines` 的公式是 `源行 = 块内行 + src_start - 1`，隐含假设"块内第 1 行 = body 第 1 行"——
即**模型报的是 body 相对行号**。但模型看到的前导区也在文件里，最自然的行为是按文件绝对行号报。

**探针实测**（fixture 前导区 18 行，块1 源区间 19-42）：

| 情形 | 模型报 | 适配器回映 | 真值 | 结果 |
|------|--------|-----------|------|------|
| 按块文件绝对行号报 body 首行缺陷 | 20 | 38 | 19 | **偏移 +19（= pre_end+1）** |
| 抱怨前导区第 3 行（docstring） | 3 | 21 | 3 | 落进 body 区间，错位 |

**测试为什么没拦住**：B7/C6 断言的就是公式本身——块内第 3 行在块文件里其实是 docstring 文本「刻意包含：」，测试把它映射到源 21 行并断言"正确"。拿实现当真值，循环论证。

**裁决办法（一分钟，用你已有的实测数据）**：任取一条真实 finding，把 claim 里引用的代码在源文件里搜出真实行号 `L_true`，与账本 locator 行号相减：
- 差值恒定 ≈ 前导区行数 + 1 → **实锤**，按下式修；
- 差值为 0 → 说明 OCR 确实报 body 相对行号，公式成立——那就在 B7 注释里把这个前提写死，补一条断言防止未来改动破坏前提。

**裁决已脚本化（`check_remap.py`，随本报告交付）**：不需要 OCR 原始产物——适配器 mapped.json、账本 case 记录（JSONL、payload 嵌套均可）、verifier 导出物都认，递归找「有 locator + quote」的 finding，quote 在源文件里定位真值行号，按源文件分组输出偏移分布 + 裁决。未分段文件天然构成控制组（偏移应恒为 0）。

```bash
python check_remap.py mapped.json --source src/big.py      # 或 cases/ --source-dir src/
```

**fixture 演跑自检**（模拟「模型按块文件绝对行号报」的世界，3 条已知向量 + 1 条控制组）：
裁决器正确输出 `偏移恒为 +19 = pre_end(18)+1 → F1 实锤 ✗`——工具对实锤路径的判别逻辑已验证可用。

**修法（若实锤）**：`load_chunk_manifest` 把 manifest 顶层的 `preamble_lines` 带出来；`remap_lines` 改为——

```python
if s <= preamble_lines:      # 前导区内的行号，本身即源行号
    return s, e, path
offset = src_start - preamble_lines - 2
```

顺手加钳制：回映结果超出 `[src_start, src_end]` 附近时告警，防止模型幻觉行号无声入库。

## F2 装饰器：错接 + 丢失，模型看到的是被改写的代码（已证实）

**机制**：Python 3.8+ 起装饰器**不算进** `FunctionDef.lineno`（指向 `def` 行）。于是：

1. `preamble_end` 用"第一个顶层 def/class 的 lineno − 1"切割 → **第一个顶层函数的装饰器整行掉进前导区**，随前导区被补进每一块。在它自己的块里侥幸重新粘回；在**其他块里悬空，粘到下一个语法对象上**。
2. 按方法切大类时，方法区间是 `m.lineno..end_lineno` → **方法自己的装饰器（@property/@staticmethod/…）被切出函数体，丢失**。

**探针证据**（第一个 def 带 @lru_cache + 大类含 @property 方法，max-lines 20 切 3 块）：

```
chunk_02_big_a.py  class 头前原文：
  import functools\nCONST = 1\n\n@functools.lru_cache\n\nclass Big:\n
  → @lru_cache 粘到 class Big 上，ast.parse 通过（语法自检抓不住语义错接）
chunk_03_big_b.py  @property 被切丢，模型看到的是裸 def big_b
```

**后果**：分段器"三条保证"只保语法不保语义。模型可能报出「lru_cache 用在类上」这类假缺陷，或漏掉依赖装饰器语义的真缺陷（路由未注册等）。**这不是转换层的"不判断对错"能豁免的——它污染的是上游输入。**

**修法（约 6 行 diff）**：

```python
def effective_start(node):
    return min([node.lineno] + [d.lineno for d in getattr(node, "decorator_list", [])])
```

`collect_items` 的区间起点和 `preamble_end` 都改用 `effective_start`：装饰器跟着函数走，前导区永不含悬空装饰器。

## F3 假报过滤：中文 claim 下是 no-op（已证实）

`_UNDEF_PAT` 只匹配英文（`not imported / NameError / undefined / missing …`）。open-code-review 在中文语境大量输出中文 claim——README 自己举的例子就是「`sqlite3` 未导入」的中文表述。

**探针实测**（对 fixture 符号表）：

| claim | 结果 |
|-------|------|
| `` `json` is never imported `` | 丢弃 ✓ |
| `` `json` 未导入 / 未定义 / 缺少导入 / 没有导入 `` | **全部保留**（闸门不匹配） |

方向仍是保守的（宁可漏杀不错杀），但意味着"坑 2 跨块假报"在中文报告下**没有被过滤**，账本会积累假缺陷记录。符号提取走反引号、语言无关，**只差闸门这一处**：

```python
_UNDEF_PAT = re.compile(
    r"(not imported|is never imported|NameError|undefined|"
    r"neither imported nor defined|missing .{0,40}(class|function|definition)|"
    r"未导入|未定义|没有导入|缺少.{0,12}(?:导入|定义))",
    re.I,
)
```

## 低危与策略项（F4–F12，按口味处理）

- **F4** `load_ocr_json`：JSON 后跟任何日志行即 `JSONDecodeError`（探针实测崩）。修法一行：`json.JSONDecoder().raw_decode(raw, idx)` 解析完即止，忽略尾部。
- **F5** `map_dimension` 关键词全英文：「安全」→ quality（应 security）。「性能」→ quality 属于巧合命中。规则表补中文关键词即可。
- **F6** `main()` 里 problems 收集后 `--post` 不检查、全量入库，退出码 2 在入库之后才返回。引擎端大概率自拒，但会留下"半批入库 + 异常中断"的账本噪音。建议：problems 非空时 `--post` 拒绝执行（fail-closed），或跳过问题条目并在 `posted_ids` 留痕。**这是策略问题，你拍板。**
- **F7** `force_rm(out)` 无条件清空 `--out`，唯一护栏是 `out == src.parent`。手滑指到仓库根/家目录直接 rmtree。建议：目标目录非空且不含 `manifest.json`/`chunk_*.py` 时拒绝，或要求 `--force`。README 写了"会被清空重建"，但护栏强度和验证器的 fail-closed 口味不一致。
- **F8** README 测试节只写 py_compile + fixture，实际有 34 例套件且 CI 在跑——README 低估了自己。B7/C6 改成"构造已知块布局 + 断言真值"（见 F1）。
- **F9** 空前导区文件（首行即 def）的块以两个空行开头（`build_chunk` 的 `f"{pre}\n\n{body}"` 未处理空 pre）；manifest 的 `failed` 只有计数，README 说"manifest 会标出缺口"——明细没写进去。
- **F10** `--chunk-manifest` 给了但 OCR 的 path 与 manifest 键对不上时，remap **静默跳过**、无统计。建议 stats 加 `remapped_count / unmatched_paths`，不匹配比例高就打警告——这正是"坑 1"复发的信号（比如 OCR 哪天开始带目录前缀报 path）。
- **F11** README 用法第一条 `python ocr_adapter.py ocr.json --json -o mapped.json`（标着"推荐先这样"）中的 `-o` **未实现**——`--help` 无此参数，原样执行报 `unrecognized arguments`（实测）。修法二选一：实现 `-o`（写文件、stdout 保留摘要），或 README 改成重定向写法。
- **F12** `build_locator_remapped` 里 `shown = source_name or path` 对**所有** finding 生效——包括 path 不在 manifest 里的（同一 OCR 会话里直接扫描的其他文件、或键不匹配的）。自检实测：控制组 finding（原始 path `other.py:3`）locator 被改写成 `tests/fixture_big.py:3`——文件名张冠李戴但行号还在，看起来完全合理。与 F10 叠加 = remap 静默失败 + 文件名被覆写 → **错误归属不可见**。另外 `_source.file` 记录的是 CLI `--source-file` 参数而非每条 comment 的原始 path，per-comment 溯源在输出里丢失。修法：仅当该 path 命中 manifest 时才用 `source_name`；`_source` 增加 `"ocr_path": c.get("path")`；未命中计数告警（即 F10 的 stats）。
