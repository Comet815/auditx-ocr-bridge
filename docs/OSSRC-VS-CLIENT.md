# Go / Rust 的数据强度：开源验过什么、没验过什么

日期：2026-11-27（接手工单任务 5）。本文只做记录与判断，不凑新数据。

## 已验的（证据在仓内与验收记录里）

| 结论 | 证据强度 |
|---|---|
| 分段几何正确：块的 body 与源文件逐字对应、body_start 回映偏移 0 | 语法层 + 开源真实文件：Go 标准库 strings.go（1304 行 → 7 块）、gin context.go（1543 行，端到端 3 条 finding、check_remap 3/3 偏移 0）、ripgrep defs.rs（8153 行 → 37 块，端到端走到账本与 V1–V11） |
| 符号表能支撑跨块假报过滤 | 同上文件的符号抽取 + 自测构造样本；**没有**真实模型断言语料验过 |
| 适配器 → 账本 → 独立验证器全链能跑通 Go/Rust | 小凛 2026-11-27 实跑（gin、ripgrep 各一条链，V1–V11 全过） |

## 没验的（开源文件推不出的结论）

1. **客户代码的分布**。标准库与 ripgrep 都是风格高度自律的开源代码。
   客户 Go 代码里的 cgo、代码生成产物（protobuf/mockgen 的大文件）、
   embed 指令、长 build tag 组合，客户 Rust 代码里的过程宏展开、
   深度泛型与 trait 套娃、workspace 多 crate 路径形态——这些形状
   一份都没在验收里出现过。分段器在这些形状上的行为是**未知**，
   不是「应该没问题」。
2. **业务语义类缺陷的检出**。适配器的跨块假报过滤与未定义闸门，
   其句式表是在 Python/JS 的真实模型断言上磨出来的。模型对 Go/Rust
   客户代码会怎么措辞（尤其 Go 的导出规则、Rust 的所有权术语），
   没有真实断言语料测过——过滤可能空转，也可能误杀，两个方向都没数据。
3. **符号表的内置名覆盖**。Go 的 len/append/make、Rust 的 prelude
   类型没有专门名表（JS 侧有 JS_GLOBALS，是被真实数据逼出来的）。
   在客户断言语料出现之前，这条只能靠构造样本守，不能宣称完备。

## 判断

开源验收证明的是**机制**：几何、回映、契约、全链贯通。这部分结论
可以对外说，证据链完整。它证明不了**分布**：真实客户代码的形状与
真实模型断言的措辞。这两类证据只能等第一个 Go/Rust 客户项目，
在此之前，凡涉及 Go/Rust 的对外表述，强度上限就是
「机制已验、分布未验」。
