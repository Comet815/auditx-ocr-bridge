# 决策记录：`.vue` 多 `<script>` 块——明确不支持（暂定）

日期：2026-11-27（接手工单任务 3）。状态：**选 B，明确不支持**，附重开条件。

## 现状（已实现且有测试锁住的行为）

- `chunk_vue.py` 只切第一个 `<script>` 块；块的行号经虚拟源填充，
  全程保持 `.vue` 文件坐标，template/style 不进审查。
- 第二个 `<script>` 块出现时，stderr 与 manifest 的 `warnings` 字段都会
  明确告警——**是留痕的不审，不是静默丢弃**。自测 V 组与仓库回归夹具
  （单块 / 双块 / 只有 import+const 的退化文件）锁住了这组行为。
- 第一个块是 `<script setup>` 时照常切分；只有 setup 块的文件走退化
  兜底，不会 0 块逃审。

## 两个选项

**A. 支持多块**：两个 script 块都切，行号仍回映 `.vue` 坐标。

**B. 明确不支持**：维持现状，把边界与理由写死在本文档与 README 边界节。

## 为什么选 B

1. **契约冻结挡着**。manifest（chunk-manifest/2）是「一个源文件一份
   前导区」：`preamble_lines` 是顶层单值。第二个块有它自己的 import 区，
   塞进同一份 manifest 就要么共用第一块的前导区（语义错误，块里会出现
   未定义的导入名，跨块假报过滤会跟着错），要么给契约加 per-block 字段
   ——而契约冻结的规矩是加字段先开 issue，不顺手改。
2. **`<script setup>` 不是普通脚本**。双块文件的常见形态是普通块放
   name/options、setup 块放逻辑（或反过来）。setup 块有编译宏
   （defineProps 等）与隐式暴露语义，把两块拼进同一个虚拟源做语法
   自检，就算 tree-sitter 不报错，块的语义边界也是假的。
3. **当前真实语料里双块是少数且形态单一**。已验过的客户代码
   （昆仑 20 个 .vue）以单块为主；双块样本只出现在自测夹具里。
   为尚未出现的分布先付契约变更的代价，不划算。

## 必须说清的代价（选 B 不等于没代价）

对通用 Vue 3 项目，双块文件里**主要逻辑可能恰在第二个
`<script setup>` 块**，此时本工具审到的是较次要的那块。缓解只有一条，
但它是硬的：第二块的存在永远会出现在 warnings 与 stderr 里，
任何一次运行都不会给人「整份文件都审过了」的错觉。审查结论引用
.vue 文件时，必须同时看 warnings——这是使用义务，写在这里。

## 重开条件（满足任一即开 issue 议契约）

- 真实项目（非夹具）出现双块 .vue 且第二块含主要逻辑；
- 客户语料里双块文件占比明显上升；
- chunk-manifest 契约因其他原因开 v3 修订时，顺带把 per-block
  前导区一并议了。

重开时的做法预判：每块独立成一组 chunks、各自带自己的前导区，
manifest 以 block 为单位记录几何——这是契约级变更，不在本决策内预支。
